# Recovering a Failed Run: Harvest First

Recover by what the journal holds and by how the script issues its calls, never by when the run died, because a resume finds its cached results by walking a chain of cache keys. On v2.1.280, the build this was read from, each agent() call's key is `v2:` followed by a SHA-256 over the key of the call before it, the prompt, and the options that shape the agent -- schema, model, effort, isolation, agentType, disallowedTools, and bashCommandClamp, serialized with sorted keys -- never the label, the phase, or `stallMs`. A run has one such chain, which starts empty and advances in the order its calls reach agent(), and that order is the run's issue order. A resume builds its own chain the same way and looks each key up in the journal: a key that carries a result replays, a key with only started events re-runs live in place without leaving replay, and any other key -- a failed one, or one the journal has never seen because an edit, a different order, or a prompt built from results that had not arrived when the first run issued that call produced it -- switches the run to live mode, after which no call is looked up in the cache at all, whatever its key. So classify every cache key (below) and read the script's shape before choosing, and default to harvest whenever either shows a resume would re-buy completed work -- read the completed calls' results out of the journal and hand them to a continuation run that spawns only the missing work.

A failed key ends replay: a call whose attempts ended in a failed event is re-run live on resume, and so is every call issued after it, cached or not, so replay stops at the earliest-issued failed key, if nothing has ended it sooner, and a single failure inside the first fan-out prices a resume at the whole run. Order here is the first run's issue order, never the order the failures reached the journal: a failed event is written only when its call gives up, and a call that stalls through all its attempts gives up long after siblings issued later have journaled their results, so a failed event's position says when the call died, not where replay stops. Read a key's issue position from its first journal event instead, and allow for setup that runs before a spawn -- creating an isolated worktree is one example -- which can let a call issued later log its first event sooner: when a failed key sits inside a fan-out, treat that whole fan-out as issued after it. A script-level retry does not repair that hole: a retry helper's later attempt is a separate call issued afterwards, so it lives under its own cache key, and its success leaves the first attempt's key failed.

The script's shape can end replay with nothing failed, because a resume does not always issue calls in the first run's order. A call the script issues after another call's result -- a pipeline's next stage, a retry, a loop that reads results -- reaches agent() when that result arrives, and on a resume a cached result arrives within milliseconds where a live call took minutes, so a branch whose results are cached can run ahead of the others and key its next call earlier than the first run did. That key folds in a different predecessor, the journal has never seen it, and the run switches to live mode there: every call keyed after it runs live, finished or not, though nothing failed and nothing was edited. Take a pipeline over two items, each a fan-out of workers followed by one merging call, whose second item finished its fan-out first: the first run keyed the first item's merge last, while a resume that gets the first item's workers back from cache can key that merge ahead of the second item's workers, and those workers, keyed behind a key the journal has never seen, then run again although their results are in it. The order holds only where no result decides when one branch issues a call relative to another: a single fan-out whose thunks each make one call keys them in input order, a strictly sequential script keys each call behind the one before it, and stages joined by barriers key all of the next stage in input order once the previous stage has returned. Timing can change more than the order. Take a call whose prompt carries whatever an unawaited call has returned by then, which this skill prescribes when it hands the settler the additional lens's text once the routed agents have returned: that call is keyed on what had arrived, and a resume returns the cached result at once. So wherever the first run issued the reading call before the unawaited result arrived, the resume builds a prompt the first run never sent; the journal has never seen that key, and the run switches to live mode there even though every barrier held.

Expect the harness to advertise the resume path whatever the journal holds. The failure notification carries a recovery line naming the resume path and nothing else; that line is a mechanism reference, not a recommendation, and taking it as one is exactly how a run that finished all its work gets paid for twice. Read the script's shape before the journal. A run in which more than one branch issues calls after results -- a pipeline() over two or more items, a fan-out whose thunks chain a second call, a result-driven loop beside other work -- goes to harvest plus a continuation whatever shape its open keys take, even when its only open call is the last one issued, because where the resume keys each call depends on which branches come back from cache first, which the journal's shapes do not show. A run whose prompt reads the result of a call nothing awaited goes to harvest as well, barriers or not, whenever the journal holds that result and its result event comes after the first started event of the call that reads it: a result that arrived after its reader started cannot have been in the reader's prompt, and the resume, which returns it at once, builds a prompt the first run never sent. A resume is the recovery only for a run whose calls keep their order -- a single fan-out, a strictly sequential script, stages joined by barriers in which no unawaited result arrived after its reader started -- and there only when no completed call was issued after a failed key, which makes it the correct and cheapest one: when every failure comes last in issue order, or the dead calls left only started events, an unchanged resume re-runs just the missing calls and replays everything else, provided the after count below confirms that the journal's new lines start every failed or started-only key again and no key that already carries a result; an order-keeping run whose failed key was issued before completed calls goes to harvest like any run whose resume would re-buy completed work. Classify before believing the line either way.

Read the breadth of the failure before opening any one transcript: when every agent in the run died, the cause is something they all shared -- the inherited tier, a shared preamble, a session setting the script never names -- and re-cutting one unit changes nothing, while a single death among returning siblings points at that unit's own input, output, or exploration budget. A run-wide wipe is a routing or configuration fault wearing a stall's clothes, and the stall signature appearing in every transcript at once is the tell.

Before interrupting, resuming, or re-running anything, diagnose from the journal, and open the diagnosis by sorting every cache key into one of three shapes. The run summary's duration, agent count, and last log line show how far the run got; the journal records a started event for every attempt, a result event when a call completes, and a failed event when a call returns null or throws, each carrying the cache key and the agent id. Under an unchanged resume -- scriptPath plus resumeFromRunId, identical script and args -- the three shapes behave differently. A key with a result replays from cache. A key whose attempts ended in a failed event is a cache hole: the resume re-runs it live under the same key, and every call issued after it runs live too. A key with started events and nothing after them is a call that was still in flight when the run was stopped, killed, or lost its process; on the builds this was read from (v2.1.280 and v2.1.288) the resume re-runs it live in place without leaving replay, so the calls keyed after it still replay while they keep the first run's order, but an earlier resume, on a build nobody recorded, was observed resolving such calls as null without re-running them -- exactly like an agent the user skipped -- so filter(Boolean) dropped them and the resumed run reported success without them. Which shape a death leaves is not the author's choice, and the started-only outcome has not held steady across observations, so classify what the journal holds rather than predicting it from the error, and confirm afterwards what actually re-ran. In a run that is still going, a key with several started events and nothing else is the agent stalling right now: its identity is the first user message of its per-agent transcript, and the transcript's tail shows how it died. One trap there: the harness records its own stall abort inside the transcript as [Request interrupted by user] -- nobody interrupted anything; that string is the stall signature, and reading it as an operator action closes the investigation on a false conclusion.

A run sitting on one open agent while every sibling has returned is a harvest, not a wait. The journal shows it directly -- every key but one carries a result, and the open key has a started event and nothing after it -- and the open agent's transcript tail says which gap holds it, and each gap has its own test for when waiting stops paying. A tool call with no matching result is a tool still running, and the stall detector is disarmed for as long as it runs, so the silence alone proves nothing -- a long build or test suite looks exactly like this while it works; the call is hung only once it has outlived that tool's own timeout, or the command budget the stage's prompt set. A tool result followed by no assistant event is a model request that never streamed, which a build that re-arms the detector after tool results, as v2.1.280 and v2.1.288 both do, aborts and retries within one window and a build that does not never aborts at all, so a transcript that has sat on that shape past its call's stall window is one the detector will not rescue. Once the open agent fails the test for its own gap, stop the run, harvest every result event as final, and finish the missing unit in the conversation or through a fresh narrow workflow keyed to the harvested results, never by waiting on an agent the detector cannot see -- an unchanged resume offers nothing better here, because at best it re-runs the same unit exactly as it was.

The two mechanics, concretely: a harvest reads the journal's result events, which carry each completed call's full structured return value, so a few lines of code recover every finished phase; a resume means stopping the run, editing the persisted script, and relaunching with scriptPath plus resumeFromRunId. One trap on the harvest: a journal result carries only the cache key and the agent id, never the label. Where the build writes the label and phase into started events (v2.1.280 and v2.1.288 do), join each result to the started event with the same agent id; otherwise identity comes from the per-agent transcript, whose first user message is the prompt -- parse the distinguishing fields you embedded there (the item id, the lens name), and classify unlabeled results by their schema shape, which is unambiguous when each phase has a distinct schema. Author for this harvest in advance: embed a stable identity marker in every fan-out prompt, because a result you cannot re-key is a result you cannot reuse. Where a completed call has no journal result, its per-agent transcript holds the value as the arguments of its last structured-output tool call -- skip transcripts without one (the harness's internal stall retries leave orphan transcripts). Use transcripts to diagnose how an agent died; use the journal to recover what it produced; and where the two disagree about a value, the transcript settles it, because it holds what the agent actually emitted.

A continuation script carries the harvested checkpoint as embedded data -- pre-fill the phase state from it, spawn agents only for the missing items, and return the same shape the original run would have, so downstream consumers cannot tell the difference. Scripts cannot read files, so a large checkpoint travels inside the script text: generate the script from a template with a placeholder and inject the JSON programmatically rather than through the conversation window, escape it to pure ASCII (raw findings routinely quote control and zero-width characters), and write the file with LF-only line endings -- the launcher rejects any script containing control characters, and a CR slipped in by platform newline translation is enough to fail the launch. Escape the data, never sanitize it away: the checkpoint must round-trip exactly.

A journal carrying no result event at all is the cheapest case to act on: nothing was cached, so a resume replays nothing and a harvest recovers nothing, and the honest recovery is a clean relaunch. Read the absence of result events as a freedom the resume path never grants -- with no cache to protect, the cache-identity discipline below is void, so prompt wording, phase structure, and model options are all free to change at once, and the right move is to rewrite the script around the defect that killed the run rather than relaunch the same shape and pay for the same death twice. A defect of that kind lives in every script authored the same way, so apply the fix across every sibling run in flight, not only the one that died first: a run still executing is not evidence of a sound script, only of a failure that has not landed yet.

Budget a resume at its worst case, which is a full re-run. Replay is prefix-shaped: it ends at the first key the resume cannot match -- a failed call, an edited one, or one keyed out of its first-run order or whose prompt took a result that had not arrived when the first run issued it -- however many results sit behind that key, so the cache can stop matching at the first fan-out even under a byte-identical script: one real interruption whose first fan-out contained nine scattered failures cut replay to nine calls out of roughly one hundred seventy-five completed. Take two counts, one before relaunching and one after. Before: events per key sorted into the three shapes, the earliest-issued failed key -- the one whose first journal event comes first, read with the fan-out allowance above -- and the journal's line count; price everything issued after that key as re-bought, and whenever the journal holds substantially more than the replay will recover, harvest into a continuation instead of resuming. After: a resume appends to the same journal rather than starting a new one, so the lines past the noted count are exactly what it did -- a new started event on a key that already carries a result is a call being paid for twice, a new started event on a key the journal has never seen is a call the first run never made or one keyed out of order, with every call keyed after it running live, a new started event on a started-only key is that call re-running, and a started-only key with no new event did not run at all -- and listing the per-agent transcript files by modification time confirms which agents actually executed. Take the after count as soon as the resume has started its first calls and again when it ends, and stop the run to harvest the moment it shows a finished call starting again. Detect re-execution from those new events and new transcripts, never from the progress counter, whose denominator differs from the original run's.

Protect cache identity when editing a script to fix a broken phase. A shared preamble embedded in every prompt is a cache-invalidation bomb: editing one word in it changes every key and re-buys everything already paid for, so keep the shared context and the per-agent instructions in separate constants, and touch only the broken phase's prompts. Byte-identical untouched keys are necessary for their own replay but never sufficient on their own: cache validity is prefix-shaped over the issue sequence, not per-key, so an edited call changes its own key and, through the chain, every key after it, and a failed call switches replay to live for every call issued after it -- across every parallel branch, regardless of whether that later call's own key changed; a started-only key is the one miss that does neither on the v2.1.280 and v2.1.288 builds, re-running in place without leaving replay, which spares the calls after it only while they keep the first run's order. Editing the prompt of an early-issued failed call -- the natural repair move, since failed calls are exactly the ones that need resume-aware rewording -- silently drops every completed call issued after it out of cache even though those calls stayed byte-identical, and relaunching then re-executes them live. Before relaunching, find where every edited or failed call was issued, by its key's first journal event, and treat everything issued after the earliest one as re-bought, not just the calls whose own text changed. A late-phase prompt that interpolates upstream results is the same bomb in another shape -- its cache identity depends on the exact serialized text, including element order after a nondeterministic stage -- so canonicalize (sort by a stable key) before interpolating.

The determinism ban on the current-time and randomness built-ins protects this same replay cache; when a timestamp or seed is genuinely needed, compute it outside the script and pass it in via args.
