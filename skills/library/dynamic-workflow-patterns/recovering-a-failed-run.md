# Recovering a Failed Run: Harvest First

Recover by what the journal holds, never by when the run died, and default to HARVEST -- read the completed calls' results out of the journal and hand them to a continuation run that spawns only the missing work. Resume is the narrow case, and ONE check decides it: scan the journal for a failed attempt anywhere before or among the calls you need replayed, because a failed attempt is a permanent cache hole that its own successful retry does not fill, so everything downstream of the earliest one is re-bought at full price. A single failure inside the first fan-out therefore prices a resume at the whole run.

Expect the harness to advertise the other answer. The failure notification carries a recovery line naming the resume path and nothing else; that line is a mechanism reference, not a recommendation, and taking it as one is exactly how a run that finished all its work gets paid for twice. Run the check before believing it.

Read the breadth of the failure before opening any one transcript: when EVERY agent in the run died, the cause is something they all shared -- the inherited tier, a shared preamble, a session setting the script never names -- and re-cutting one unit changes nothing, while a single death among returning siblings points at that unit's own input, output, or exploration budget. A run-wide wipe is a routing or configuration fault wearing a stall's clothes, and the stall signature appearing in every transcript at once is the tell.

Before interrupting or re-running anything, diagnose from the journal. The run summary's duration, agent count, and last log line reveal how far the run got, and the journal records one started event per attempt and one result event per completed call, both carrying the cache key and agent id: a key with several started events and no result is the stalling agent, its identity is the first user message of its per-agent transcript, and the transcript's tail shows how it died. One trap there: the harness records its own stall abort inside the transcript as [Request interrupted by user] -- nobody interrupted anything; that string is the stall signature, and reading it as an operator action closes the investigation on a false conclusion.

The two mechanics, concretely: a harvest reads the journal's result events, which carry each completed call's full structured return value, so a few lines of code recover every finished phase; a resume means stopping the run, editing the persisted script, and relaunching with scriptPath plus resumeFromRunId. One trap on the harvest: a journal result carries only the cache key and the agent id, NEVER the label, so identity comes from the per-agent transcript, whose first user message is the prompt -- parse the distinguishing fields you embedded there (the item id, the lens name), and classify unlabeled results by their schema shape, which is unambiguous when each phase has a distinct schema. Author for this harvest in advance: embed a stable identity marker in every fan-out prompt, because a result you cannot re-key is a result you cannot reuse. Where a completed call has no journal result, its per-agent transcript holds the value as the arguments of its last structured-output tool call -- skip transcripts without one (the harness's internal stall retries leave orphan transcripts). Use transcripts to diagnose how an agent died; use the journal to recover what it produced; and where the two disagree about a value, the transcript settles it, because it holds what the agent actually emitted.

A continuation script carries the harvested checkpoint as embedded data -- pre-fill the phase state from it, spawn agents only for the missing items, and return the same shape the original run would have, so downstream consumers cannot tell the difference. Scripts cannot read files, so a large checkpoint travels inside the script text: generate the script from a template with a placeholder and inject the JSON programmatically rather than through the conversation window, escape it to pure ASCII (raw findings routinely quote control and zero-width characters), and write the file with LF-only line endings -- the launcher rejects any script containing control characters, and a CR slipped in by platform newline translation is enough to fail the launch. Escape the data, never sanitize it away: the checkpoint must round-trip exactly.

A journal carrying no result event at all is the third case, and it is the cheapest one to act on: nothing was cached, so a resume replays nothing and a harvest recovers nothing, and the honest recovery is a clean relaunch. Read the absence of result events as a freedom the resume path never grants -- with no cache to protect, the cache-identity discipline below is void, so prompt wording, phase structure, and model options are all free to change at once, and the right move is to rewrite the script around the defect that killed the run rather than relaunch the same shape and pay for the same death twice. A defect of that kind lives in every script authored the same way, so apply the fix across every sibling run in flight, not only the one that died first: a run still executing is not evidence of a sound script, only of a failure that has not landed yet.

Budget a resume at its worst case, which is a full re-run. Replay is prefix-shaped: completion order inside a concurrent stage is nondeterministic, so the cache can stop matching at the first fan-out even under a byte-identical script, and a failed attempt's successful retry lives under a different cache key -- one real interruption whose first fan-out contained nine scattered failures cut replay to nine calls out of roughly one hundred seventy-five completed. Estimate before relaunching, not after: count the journal's result events, find the EARLIEST failed attempt among them, and price everything downstream of it as re-bought. Whenever the journal holds substantially more than the replay will recover, harvest into a continuation instead of resuming. Confirm what actually replayed (a started event on a key that already carries a result is a call being paid for twice), and detect re-execution from new transcripts appearing, never from the progress counter, whose denominator differs from the original run's.

Protect cache identity when editing a script to fix a broken phase. A shared preamble embedded in every prompt is a cache-invalidation bomb: editing one word in it changes every key and re-buys everything already paid for, so keep the shared context and the per-agent instructions in separate constants, and touch only the broken phase's prompts. Byte-identical untouched keys are necessary for their own replay but never sufficient on their own: cache validity is prefix-shaped over the journal SEQUENCE, not per-key, so an edited call or a failed call invalidates every call journaled AFTER it, across every parallel chain, regardless of whether that later call's own key changed. Editing the prompt of an early-journaled failed call -- the natural repair move, since failed calls are exactly the ones that need resume-aware rewording -- silently drops every later-journaled completed call out of cache even though those calls stayed byte-identical, and relaunching then re-executes them live. Before relaunching, confirm the journal position of every edited or failed call and treat everything journaled after the earliest one as re-bought, not just the calls whose own text changed. A late-phase prompt that interpolates upstream results is the same bomb in another shape -- its cache identity depends on the exact serialized text, including element order after a nondeterministic stage -- so canonicalize (sort by a stable key) before interpolating.

The determinism ban on the current-time and randomness built-ins protects this same replay cache; when a timestamp or seed is genuinely needed, compute it outside the script and pass it in via args.
